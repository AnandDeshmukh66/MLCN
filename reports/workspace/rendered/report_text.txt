ABSTRACT
Network  intrusion  detection  requires  a  consistent  transformation  from  observed 
packets to the numerical representation used by a trained classifier. This project 
investigates Machine Learning Cybersecurity Network (MLCN), a laboratory platform 
connecting  packet  capture,  parsing,  bidirectional  flow  construction,  24-feature 
extraction  and  five-class  XGBoost  inference.  The  current  repository,  training 
notebook, model artifacts and validation logs are audited, and all 251,812 saved test 
predictions  are  independently  replayed.  Offline  accuracy  is  99.4238%,  balanced 
accuracy is 99.5568%, and macro F1 is 0.93358. Brute Force precision remains 
limited to 53.1378%, with 799 false positives. Current code corrects the historical 
timing-unit mismatch by using microsecond timing features and per-second rates. 
Saved laboratory records provide narrower evidence of selected-profile recognition 
and are separated from synthetic demonstration output. Six of 202 executed tests fail 
in demonstration labelling or presentation behavior. A Gemini-based explanation 
workflow is proposed with explicit evidence, privacy and uncertainty controls; it is not 
implemented. The findings support a connected research prototype while identifying 
reproducibility,  provenance  and  live-validation  requirements  before  broader 
deployment.

Chapter 1
Introduction
1.1 Background and context
Machine Learning Cybersecurity Network (MLCN) is a laboratory implementation of 
flow-based network intrusion detection. An intrusion detection system (IDS) observes 
activity and identifies patterns that warrant investigation. A network IDS derives these 
observations from communication traffic. It differs from a preventive control because 
a classification does not itself block a connection or establish that a compromise 
occurred. MLCN connects packet capture, parsing, conversation assembly, numerical 
feature extraction and supervised classification in one executable processing chain.
The practical difficulty is maintaining agreement between the data representation used 
during model development and the representation produced by a running network 
monitor. A high score on previously extracted rows cannot demonstrate that live 
packets are grouped, measured and classified correctly. Sommer and Paxson [1] 
identify the gap between controlled machine-learning evaluations and operational 
intrusion detection. In MLCN, this concern becomes concrete through timing units, 
payload accounting, flow termination and the distinction between genuine model 
predictions and demonstration output.
The  present  investigation  examines  the  repository  at  commit 
95407efc1f5d2b413abc36b24824481df97f7306, together with the local files available 
during the audit of 21 October 2026. The supplied implementation guide provides 
orientation, but current executable code and saved artifacts determine the technical 
findings. The report is an assessment of the observed implementation and its evidence, 
rather than a claim that every feature mentioned in the root README has been 
completed. The report follows the supplied institutional academic-year template, 2025
–26; the actual submission date remains subject to student confirmation.

1.2 Network traffic and flow-based classification
Individual packets carry addresses, protocol identifiers, flags and payload. Many 
useful indicators depend on relationships among packets: the balance of requests and 
responses,  elapsed  time,  inter-arrival  gaps  and  characteristic  message  lengths.  A 
bidirectional flow groups packets belonging to the same pair of transport endpoints 
and protocol. Aggregating such packets provides a compact representation for a 
classifier,  while  retaining  enough  temporal  and  directional  structure  for  several 
common traffic categories.
The  Canadian  Institute  for  Cybersecurity  (CIC)  publishes  CIC-IDS2017  as  an 
intrusion-detection dataset with packet captures and labelled flow records [2]. The 
local MLCN workspace contains eight MachineLearningCVE comma-separated-value 
(CSV) files associated with that dataset and a notebook that selects five output classes. 
The measured unit of evaluation is a row representing a flow. The 2,830,743 rows 
found across these files must therefore not be described as an equivalent number of 
captured packets.
The  implemented classifier predicts  BENIGN, Brute Force, distributed denial  of 
service (DDoS), denial of service (DoS), or Port Scan. BENIGN is the non-attack 
class, so the system contains four attack labels and one normal label. These classes do 
not  cover  all  hostile  activity.  The  notebook  excludes  other  original  categories, 
including Bot, Web Attack, Infiltration and Heartbleed, from the final five-class task. 
A prediction is consequently a choice within a restricted label vocabulary, not an 
open-ended assessment of all network threats.
1.3 Motivation and problem statement
The project is motivated by the need to make a trained network classifier observable as 
a complete system. A classifier deployed without documented packet semantics can 
receive plausible-looking but incompatible inputs. Conversely, a functioning capture 
interface can produce no useful predictions if flows never reach the completion 
boundary or if traffic falls outside the model’s classified protocols. Both types of 
failure can be hidden by a user interface that displays a desired profile instead of the 
actual detector output.


--- PDF PAGE 15 ---
3
The problem addressed is to implement and assess an auditable conversion from 
observed network packets to a fixed 24-feature vector and a five-class prediction. The 
associated research questions are whether the repository preserves a consistent feature 
contract; whether its saved offline results can be independently reproduced; what the 
available  laboratory  records  establish  about  live  operation;  and  what  additional 
evidence  is  necessary  before  an  explanation  service  can  responsibly  describe  a 
detection.
Extreme Gradient Boosting (XGBoost), developed by Chen and Guestrin [3], supplies 
the tree-ensemble classifier. Its use is technically appropriate for structured numerical 
inputs, but the algorithm’s general success does not establish performance on an 
unseen  network.  The  report  therefore  treats  algorithm  selection,  implementation 
correctness, statistical evaluation and deployment validity as separate questions. This 
separation also prevents a  demonstration profile  match from  being mistaken for 
independently labelled attack detection.
1.4 Scope and boundaries
The verified scope includes five connected processing modules, a trained XGBoost 
artifact,  a  training/evaluation  notebook,  local  CIC  flow  data,  a  bounded  traffic 
generator, receiver services, a Windows launcher, a Streamlit operations console, 
validation utilities and tests. The pipeline retains genuine results in memory and can 
emit structured detection records through its command-line interface (CLI). A separate 
demonstration transformation can alter displayed predictions when explicitly enabled 
or enabled by launcher defaults; its presence is central to interpreting the evidence.
The project does not verify network-wide visibility, high-volume capture reliability, 
autonomous  remediation,  authentication  of  an  attacker,  identification  of  malware 
families or generalization to arbitrary environments. The implemented feature vector 
contains no direct application credential content. The Brute Force generator produces 
labelled laboratory request/deny exchanges rather than guessing real credentials. The 
DDoS-labelled profile is bounded local traffic from the generator, so it is not evidence 
of a distributed attack campaign or a service outage.

Chapter 2
Review of Literature
2.1 Review strategy
The review concentrates on work that helps assess the implemented task: flow-based 
supervised classification, tree ensembles, traffic-data quality, imbalanced evaluation 
and explanations. Sources are checked through original papers, author-maintained 
research pages, dataset-provider websites and patent publication records. Search terms 
include  “machine  learning  network  intrusion  detection”,  “flow  classification”, 
“CICIDS2017  feature  extraction”,  “precision  recall  imbalanced  datasets”  and 
“adaptive  network  intrusion  detection  patent”.  Verification  is  performed  on  21 
October 2026.
The review is selective rather than exhaustive. It does not combine accuracy figures 
from incompatible datasets into an apparent league table. Differences in labels, class 
balance, sampling, preprocessing and train/test separation can dominate an algorithm 
comparison. The comparisons below instead identify methodological choices and their 
relevance to MLCN. Numerical comparisons within this report are restricted to the 
same saved evaluation population or are clearly labelled as results from a different 
evidence level.
2.2 Intrusion-detection approaches and operational context
Signature-based detection searches for predefined evidence of known activity, whereas 
supervised classification learns relationships between labelled examples and outputs. 
Anomaly detection estimates a reference distribution and flags deviations. These 
approaches  answer  different  questions:  deviation  from  a  baseline  need  not  be 
malicious, and membership in a learned attack class does not establish the precise 
cause  of  an  event.  MLCN  implements  supervised  multiclass  classification,  even 
though parts of its motivation use the broader language of anomaly detection.
Sommer and Paxson [1] emphasize the difficulty of transferring machine learning into 
open operational environments. Their discussion motivates a requirement for realistic

benign traffic and an understanding of the cost of errors. The present report applies 
that  requirement  by  examining  Brute  Force  precision  separately  from  aggregate 
accuracy  and  by  refusing  to  treat  generated  laboratory  labels  as  independently 
established truth.
Handley, Paxson and Kreibich [4] study ambiguity between traffic observed by a 
network monitor and traffic interpreted by endpoints. Their traffic-normalization work 
is conceptually different from MLCN’s statistical classifier, but it highlights why 
capture semantics matter. The local pipeline parses packets independently and does 
not  reconstruct  complete  application  sessions.  Its  predictions  therefore  inherit 
uncertainty  from  missing  packets,  segmentation,  reordering  and  visibility  across 
interfaces.
2.3 Boosted trees and the implemented model choice
Chen and Guestrin [3] present XGBoost as a scalable tree-boosting system with 
regularization  and  engineering  techniques  for  efficient  learning.  For  MLCN,  the 
relevant property is the ability to model nonlinear relationships among numerical flow 
features without adding a learned scaling stage. The repository’s final training cell 
uses a multiclass probability objective and histogram-based tree construction. These 
are code-verified choices, not deductions from the article.
A single decision tree offers a small rule structure but may be sensitive to training 
variation. A random forest averages multiple trees, while boosting constructs an 
additive ensemble whose later steps reduce the objective remaining after earlier steps. 
A  neural  network  can  represent  complex  interactions  but  introduces  additional 
architectural and optimization choices. These are methodological alternatives; the 
repository does not supply matched final test artifacts for them. MLCN’s saved 
XGBoost results cannot establish superiority over these alternatives without controlled 
experiments.
The key empirical question is not whether boosted trees are powerful in general, but 
whether the chosen representation remains stable from training to live operation. A 
tree threshold learned in microseconds will not retain the same meaning if seconds are

2.4 Traffic datasets and representation compatibility
CIC-IDS2017  provides  a  relevant  source  because  its  labelled  flows  and  attack 
categories  overlap  the  implemented  classifier.  The  provider  describes  a  five-day 
collection period, 3–7 July 2017, and traffic processed through CICFlowMeter [2]. 
The notebook’s introductory statement about seven days is therefore not retained as a 
verified dataset fact. Local CSV names and raw row counts corroborate the presence 
of the eight daily/attack-specific files; they do not independently certify the origin of 
every row against a provider checksum.

2.5 Evaluation under imbalance and distribution shift
Arp, Quiring, Pendlebury, Warnecke, Pierazzi, Wressnegger, Cavallaro and Rieck [8] 
review common pitfalls in machine-learning security research. Their recommendations 
motivate checking data provenance, evaluation design and the connection between a 
measured task and a security claim. The present audit finds a stratified row split in the 
notebook,  along  with  preprocessing  performed  before  splitting.  This  is  stronger 
evidence than an unknown split procedure, but it leaves dependence among related 
flows and preprocessing leakage as concrete concerns.
Saito  and  Rehmsmeier  [9]  explain  why  precision–recall  views  are  valuable  for 
imbalanced classification. MLCN’s Brute Force class is only 915 of 251,812 test rows. 
Its high recall is compatible with low precision because a small fraction of the much 
larger  benign  population  can  create  many  false  alerts.  Reporting  both  receiver 
operating characteristic (ROC) and precision–recall (PR) curves helps expose the 
difference between score ranking and a selected decision rule.
An area under the ROC curve (ROC-AUC) summarizes ranking across thresholds; it is 
not a statement that every deployed alert has that probability of being correct. The 
current multiclass decision rule selects the greatest probability without a separate 
rejection  threshold.  Its  precision  is  evaluated  at  that  specific  operating  point. 
Probability calibration, threshold selection and out-of-distribution rejection would 
require their own validation protocol, preferably using a population representative of 
the intended deployment.
2.6 Explainability and narrative reporting
Lundberg and Lee [10] introduce SHapley Additive exPlanations (SHAP), an additive 
feature-attribution  framework.  Ribeiro,  Singh  and  Guestrin  [11]  develop  Local 
Interpretable  Model-agnostic  Explanations  (LIME),  based  on  local  surrogate 
explanations. These methods seek to relate a model output to input features under their 


--- PDF PAGE 22 ---

respective assumptions. Neither establishes that a suspicious network event caused an 
intrusion, and neither is verified as an implemented MLCN component.
A  large  language  model  (LLM)  can  translate  supplied  evidence  into  a  readable 
incident narrative. That ability is distinct from calculating an attribution. A Gemini 
response should not invent a statement that “high SYN count caused the prediction” 
when no attribution was computed and the named column follows a nonstandard flag 
mapping. The proposed design therefore uses a factual evidence contract and reports 
attribution as unavailable unless a separate, validated method has produced it.
Google’s Gemini documentation describes schema-constrained structured output using 
JavaScript Object Notation (JSON) [12]. Syntactic conformity is useful for reliable 
integration, but it cannot establish factual correctness. The proposal in Chapter 3 adds 
evidence  identifiers,  numerical  consistency  checks,  explicit  uncertainty  and  a 
deterministic  fallback.  This  is  a  system-design  recommendation  for  MLCN;  no 
application programming interface (API) execution or explanation-quality result is 
claimed.

3.4 Module 1: packet capture
PacketCaptureEngine in packet_capture/capture.py resolves an interface or a comma-
separated interface list and invokes Scapy sniff with store=False and a one-second 
timeout. A Berkeley Packet Filter (BPF) expression can restrict traffic to a laboratory 
port or port range. The callback path capture_metadata is the integration interface used 
by the pipeline. Separate display-oriented methods preserve the packet-capture CLI 
and its ParsedPacket representation.
Single-interface  capture  runs  directly;  multiple  interfaces  create  daemon  worker 
threads.  The  implementation  installs  signal  handlers  only  from  the  main  thread, 
allowing background validation to start without an illegal signal registration. On 
Windows,  Ctrl+Break  support  helps  the  launcher  stop  a  child  process  group. 
Permissions and interface errors are surfaced through user-facing CLI messages. In 
contrast, callback exceptions are generally logged at debug level and suppressed so 
that capture can continue.
The use of store=False prevents Scapy from retaining its own full packet list, but it 
does  not  make  the  whole  application  constant-memory.  The  flow  builder  stores 
metadata and the pipeline retains completed results. Multiple interface workers can 
also call into shared flow state without an explicit pipeline lock. This is a code-level 
concurrency concern, not a measured corruption result. No packet deduplication, 
capture-loss measurement or global ordering queue is verified.
3.5 Module 2: packet parsing and normalization
The packet parser accepts a Scapy Packet and returns PacketMetadata or None. It 
normalizes  timestamps  to  timezone-aware  Coordinated  Universal  Time  (UTC), 
validates Internet Protocol (IP) addresses, bounds port numbers, extracts Transmission 
Control Protocol (TCP) or User Datagram Protocol (UDP) fields, and records packet 
length. IPv4 time to live and IPv6 hop limit are exposed as metadata, together with 
TCP window information when applicable. These auxiliary fields are not all included 
in the 24-feature model vector.


--- PDF PAGE 29 ---
17
Non-IP frames can produce metadata with absent addresses; such records are later 
unable to form a valid flow key. Malformed objects, unusable lengths and invalid 
addressing are skipped. TCP flags are normalized into a compact letter representation. 
The  parser  recognizes  Internet  Control  Message  Protocol  (ICMP)  for  metadata 
purposes, but the integrated classifier subsequently excludes protocols other than TCP 
and UDP. Parsing support must therefore not be confused with classification coverage.
Fig.  3.3  shows  the  transformation  from  packets  into  eligible  flows.  The  parser 
distinguishes  observed  packet  length  from  transport  payload  length.  Payload 
accounting subtracts Scapy padding already represented in the transport payload and 
applies an IPv4 minimum-frame padding adjustment. This is a compatibility rule 
intended to align short-packet lengths with the historical CIC-derived representation. 
IPv6 does not follow that IPv4 padding branch. The report does not claim independent 
packet-capture equivalence for every protocol or platform.

3.6 Module 3: bidirectional flow construction
A FlowKey is constructed from source address, destination address, source port, 
destination  port  and  normalized  protocol.  The  endpoint  pairs  are  sorted 
lexicographically, using a sentinel only when a port is absent. A packet and its reverse

lookup convention; it is not a declaration that the smaller address is the client or that 
the key’s source endpoint initiated the connection.
The mutable _ActiveFlow stores the first arrival’s direction as its forward orientation 
and appends subsequent metadata. It tracks packet counts, observed byte counts, 
direction-specific counts and timestamps. Completion creates an immutable Flow with 
the packet tuple and a closed_by_fin flag where appropriate. Fig. 3.4 separates the 
identity of the conversation from its direction convention. This distinction is necessary 
when explaining directional features or interpreting logs whose canonical source is the 
receiver port.
Fig. 3.4 Bidirectional key construction and orientation. Canonical endpoint ordering and forward-

The generic FlowBuilder defaults are a 60-second inactivity timeout, a 300-second 
maximum duration, 100,000 active flows and FIN termination disabled. The integrated 
pipeline overrides the maximum duration to 120 seconds and enables FIN termination 
through  the  feature  contract.  The  launcher  separately  shortens  inactivity  to  five 
seconds for laboratory runs. A report that quotes only the standalone class defaults 
would misdescribe the actual integrated system.
On each accepted packet, the builder first expires flows that have exceeded the 
inactivity limit relative to that packet’s timestamp. For an existing key, it also checks 
maximum age before appending. A FIN packet appended to an existing flow can close 


--- PDF PAGE 31 ---
19
it immediately; a first packet starting a new flow is not subjected to the same post-
append FIN branch. Capacity eviction selects the least recently seen active flow, and 
an explicit flush closes every remaining flow. TCP reset alone is not a configured 
termination condition.
The expiration scan traverses active flows, so add_packet is not constant-time in the 
number of active conversations. During a completely silent capture, no background 
timer in the builder independently expires idle flows. A later packet or explicit 
shutdown flush triggers completion. This explains why an idle timeout is not itself a 
guaranteed maximum alert delay. The same code also updates end_time in arrival 
order, whereas feature extraction later sorts packet timestamps; out-of-order arrivals 
can therefore create differences between displayed duration and the model’s duration 
feature.

3.7.2 Payload lengths, rates and direction ratio
For each packet, the extractor uses payload_length when available and falls back to 
observed  length  otherwise.  Directional  totals  sum  payload  bytes,  and  directional 
means divide by the relevant packet count. The overall Packet Length Mean and 
Packet Length Std use the series consisting of the first payload followed by all 
payloads. The first value is therefore counted twice, producing n + 1 observations. 
This is intentional local compatibility behavior and must not be rewritten as the 
ordinary mean of n packet lengths.
For nonzero duration, Flow Bytes/s = total payload bytes × 10⁶ / D and Flow Packets/s 
= n × 10⁶ / D. The displayed flow duration remains in seconds. If D is zero, the 
extractor  supplies  the  recorded  training  rate-fill  constants:  3715.0378579999997 
payload bytes/s and 69.742244285 packets/s. These values preserve the documented 
preprocessing convention; they are not measurements of an instantaneous physical 
rate.
Down/Up Ratio is floor(n_b / n_f), with zero when no forward packets exist. It is not 
forward divided by backward, and it is not a fractional ratio. For example, three 
backward packets and two forward packets yield 1.0. This correction is important 
because the supplied guide describes the older inverse convention. The removal of 
Average Packet Size from the candidate schema is described as near-duplication, not 
exact algebraic equivalence under the current n + 1 length semantics.
3.7.3 First-packet flags and activity periods
The six feature columns named Flag Count are binary indicators of the first sorted 
TCP packet. The contract maps FIN Flag Count to R, SYN Flag Count to P, RST Flag 


--- PDF PAGE 34 ---
22
Count to C, PSH Flag Count to S, ACK Flag Count to A, and URG Flag Count to F. 
The  names  thus  preserve  dataset-compatible  column  semantics  rather  than 
conventional names for accumulated TCP flags. Non-TCP packets contribute zero to 
these  binary  indicators.  Any  future  explanation  must  use  this  mapping  when 
describing what was actually observed.
Active and idle periods are derived from gaps greater than five million microseconds. 
Such a gap closes a preceding positive active span and is recorded as idle. The final 
active span is not added. If the flow was closed by FIN, the final closing packet is 
excluded from activity-state updates. A short uninterrupted flow can consequently 
have Active Mean equal to zero even though communication occurred. The feature is a 
statistic of recorded segmented periods, not the total amount of time the host was 
working.
3.7.4 Input validation and remaining semantic risks
FeatureVector enforces the vector length and provides mapping, tuple and list views. 
Integer-schema values are converted through integer coercion and then represented as 
floats. The model boundary verifies that all supplied values are finite. A raw sequence 
has no semantic names attached beyond its position, so order correctness remains the 
caller’s responsibility. The from_mapping helper fills missing names with zero; this 
convenience is not a substitute for verifying completeness in an external ingestion 
service.
The current code repairs the guide’s seconds-versus-microseconds mismatch. Feature 
names, units and order agree across the contract and model metadata. However, this 
establishes  a  local  contract  rather  than  universal  equivalence  to  every  historical 
CICFlowMeter output. Timing resolution, retransmissions, padding, packet loss, FIN 
behavior and mid-flow starts can still alter the representation. Independent packet-
level reference captures remain necessary to validate those boundary cases.

3.10 Pipeline orchestration, completion and output
IntrusionDetectionPipeline  accepts  raw  packets,  parsed  metadata,  batches  or  live 
capture. It owns the builder, feature engine and detector, exposes counters, and 
supports reset, flush and close. Completed flows must contain at least two packets and 


--- PDF PAGE 38 ---
26
use TCP or UDP to be classified. A pipeline detection combines the completed flow, 
feature vector and genuine detector result. The genuine result is appended to internal 
results before the optional display transformation is applied to the callback copy.
The CLI can print class, confidence, endpoint key, observed packet and byte counts, 
duration and all five probabilities. Its --detections-log option appends one JSON object 
per  displayed  result,  including  genuine  prediction  fields  and  a  demo_fallback 
indicator. The serialization does not include the complete feature vector, even though 
the in-memory PipelineResult retains it. Existing JSON Lines (JSONL) files therefore 
support prediction analysis but cannot fully reconstruct the feature evidence for an 
explanation service.
The pipeline catches feature-extraction or detection exceptions and continues. Such 
failures  are  debug-logged  but  do  not  have  a  dedicated  failed-flow  counter.  The 
accepted-packet counter increments before checking whether usable addressing exists, 
and can therefore include metadata later rejected by the flow builder. These details 
limit  the  interpretation  of  counters  as  throughput  or  success  metrics.  A  future 
operational version should distinguish parsed, flow-eligible, classified, intentionally 
skipped and failed observations.
3.11 Traffic profiles, parameter mapping and generation
The profile JSON stores empirical reference statistics and a source-population count of 
2,518,112.  profile_loader  reads  medians  and  discriminative-feature  blocks,  and 
parameter_mapper converts those values into bounded connection, delay and payload 
settings. The profile numbers are reference statistics, not the actual observed 24-
feature vector. Fig. 3.8 shows the separation between the profile, traffic stimulus, 
capture and detector.


--- PDF PAGE 39 ---
27
Fig. 3.8 Generator/receiver interaction and evidence paths. Profile reference medians do not bypass

Five generator classes implement distinct laboratory shapes. BenignTrafficGenerator 
performs ordinary request/response exchanges. PortScanTrafficGenerator uses TCP 
connect probes over a bounded range; a field named send_syn_only does not turn it 
into  a  raw  SYN-only  packet  generator.  BruteForceTrafficGenerator  uses  a  line-
oriented laboratory session with six request/deny exchanges. DDoSTrafficGenerator 
requests  a  small  laboratory  path  with  bounded  concurrency,  while 
DoSTrafficGenerator sends browser-like requests in bursts separated by pauses.
The configured page response is 11,600 bytes; the DoS request builder targets 330 
bytes and the DDoS request is a short Hypertext Transfer Protocol (HTTP) request. 
These shape choices are implementation details used to approximate selected training-
flow patterns. They should not be interpreted as genuine exploitation or as proof that 
the response semantics match every member of a dataset attack class. The sender’s 
packets_sent counter records application send operations and is not a measured count 
of packets on the wire.
The controller validates a private/local target, port and duration, manages a stop event 
and worker thread, records progress, and writes a structured generator run log. Target 
checks reject public destinations and support a documented private/loopback policy. 
The configuration declares caps of 300 seconds, 20 connections/s, 50 packets/s, ten 
concurrent  connections,  fifty  ports  and  512  payload  bytes.  These  are  laboratory 


--- PDF PAGE 40 ---
28
controls; not every constant is a packet-level enforcement mechanism, and receiver 
page bytes are distinct from the generator’s payload parameter.
3.12 Receiver services and validation modes
LabEchoServer  binds  a  laboratory  endpoint  and  handles  connections  in  worker 
threads.  It  returns  a  fixed  page  for  the  configured  page  paths  and  responds  to 
laboratory authentication-like lines with a denial line. receiver_server exposes this 
service  as  a  CLI  for  a  separate  receiver.  Connectivity  helpers  probe  endpoint 
availability and offer platform-specific capture guidance. A TCP service must be 
available  for  request/response  profiles,  whereas  a  closed-port  response  can  be 
meaningful to a port-probe profile.
LocalValidationRunner can  start  the  actual  pipeline  on  loopback  and  collect  in-
memory results. It converts them into ValidationRecord objects containing target 
profile, prediction, probabilities and all observed feature values. Its stop method closes 
the pipeline and joins the worker with a timeout, but the pipeline’s locally created 
capture engine is not exposed for an explicit stop request. This is a lifecycle concern: 
closing the classifier path does not itself demonstrate that a background sniff loop has 
terminated cleanly.
The launcher’s validation utility runs profiles sequentially, records time windows and 
compares genuine predictions for connection-opening flows. Its opening-flow criterion 
is an initial flag string exactly equal to S. The denominator therefore excludes closing-
handshake tails and other flows that do not satisfy the criterion. This restricted match 
fraction is useful for a controlled demonstration, but is not the same statistic as end-to-
end  accuracy  over  all  classified  flows  or  recall  against  independently  verified 
malicious events.
3.13 Windows launcher and process lifecycle
start_mlcn.bat  selects  an  available  project  Python  executable  and  invokes 
mlcn_launcher.  The  launcher  checks  platform,  Npcap  availability,  administrative 
requirements, interface discovery, model readiness and relevant ports. It identifies the 
local adapter and the Npcap loopback device, starts the receiver service and pipeline, 


--- PDF PAGE 41 ---
29
and manages the Streamlit child process. Child environments configure UTF-8 output, 
the single-PC mode, the session file and demonstration fallback behavior.
The process wrapper gives each child an independent process group where supported. 
Shutdown attempts an interrupt, then termination and finally kill if required. The 
launcher’s default LaunchConfig enables demo_fallback, uses lab port 8080 and a 
fifty-port span, and sets inactivity to five seconds. A --no-demo-fallback launcher 
option is available. Reproducible scientific validation must record this option or 
equivalent environment setting, rather than relying on a launcher default intended for 
presentation.
3.14 Streamlit console and demonstration provenance
The current Streamlit application is a two-panel operations console. The left panel 
controls loopback generation at 127.0.0.1. The right panel reads receiver JSONL 
records and presents a final session result or latest flow, probabilities, flow metadata 
and recent history. The reader tails at most 512,000 bytes, tolerates incomplete JSON 
lines and filters by recording time. This is implemented receiver visibility, correcting 
the older guide’s claim that Streamlit has only generator-side status.
Demonstration fallback creates a synthetic five-class probability distribution when the 
genuine class differs from the selected profile. Its synthetic selected-class confidence 
is  sampled  between  0.91  and  0.975.  The  genuine  prediction  remains  available 
separately. Session verdicts apply a 90% opening-flow match rule and also check the 
aggregate class. Synthetic distributions represent presentation behavior and cannot be 
included in accuracy, calibration or explanation-quality measurements.

source  or  a  per-flow  demo_fallback  boolean.  A  session  record  using  “Fetching 
RESULT” lacks that boolean, creating a risk of mislabelling its displayed source. The 
six  observed  test  failures  include  expectations  affected  by  this  terminology  and

presentation drift. The report therefore uses the explicit term synthetic demonstration

3.15 Test architecture and integration evidence
The tests cover packet normalization, module handoffs, canonical keys, timeouts, 
feature calculations, schema validation, real saved-model inference, pipeline lifecycle, 
laboratory generators, launcher behavior, dashboard parsing and fallback logic. Some 
tests patch sniff or construct packets directly. tests/lab_traffic_simulation.py explicitly

Successful tests using those sequences establish consistency under the simulated 
inputs, not successful capture from a physical interface.
The audit executes the complete unittest suite. An initial sandboxed run encounters 
three socket-binding errors in addition to six assertion failures. A rerun with loopback

six failures out of 202. The tests that load the real classifier and exercise the simulated 
profile chain pass in that run. Chapter 4 interprets the failures and keeps this evidence 
separate from saved Windows-oriented validation records.
3.16 Proposed Gemini XAI architecture
The proposed workflow is genuine prediction plus associated evidence, followed by a 
structured Gemini request, validated explanation generation and a human-readable 
report.  Fig.  3.9  identifies  every  new  element  as  proposed.  It  operates  after 
classification so that a language-model timeout cannot delay or replace the underlying 
detector.  No  network  call  to  Gemini  is  made  during  this  investigation,  and  no 
application implementation is added.

3.16.1 Input contract and grounding
A proposed EvidenceEnvelope contains an evidence identifier, capture timestamp, 
flow identifier, model hash, feature-schema version, genuine class, all five genuine 
probabilities, feature values with units, capture-quality flags and provenance status. 
The classification component supplies these fields from the in-memory result or an 
expanded future evidence sink. The current JSONL export is insufficient for complete 
feature grounding because it omits the feature vector. Appendix V provides the 
proposed contract as an interface specification rather than as a recorded API payload.
The envelope explicitly rejects a synthetic displayed distribution as model evidence. If 
a  demo_fallback  record  is  encountered,  the  service  may  use  separately  verified 
genuine  fields  only  when  their  provenance  is  complete;  otherwise  it  returns  an 
insufficient-evidence summary. Feature values are validated for finiteness, order, units 
and schema version. The flag mapping is included in explanatory metadata so that a 
column name cannot be interpreted as a conventional count without checking its 
definition.
Each  explanatory  observation  cites  an  evidence  identifier  and  a  field  path.  For 
example,  a  statement  about  Flow  Duration  cites  its  microsecond  value  and  any 
displayed conversion to seconds. The system does not claim that a feature caused the 


--- PDF PAGE 44 ---
32
decision merely because its value is large. Optional SHAP contributions would arrive 
through  a  separate  attribution  object  with  its  method,  model  version, 
background/reference definition and output space. If absent, the report states that 
feature attribution was not computed.
3.16.2 Request and response design
The proposed request separates trusted instructions from untrusted evidence values. A 
versioned  instruction  specifies  the  task,  permitted  evidence,  class  vocabulary, 
uncertainty language and JSON response schema. Evidence is serialized as data rather 
than concatenated into free-form instructions. A model identifier is configured and 
logged at deployment time; the report avoids selecting an unverified future model 
name. Structured output is used for parseability, with semantic validation performed 
locally after generation.
The response contains a factual summary, evidence-linked observations, limitations, 
alternative explanations, recommended human checks and a provenance block. It 
repeats the genuine prediction without changing its label or probabilities. It avoids 
unsupported statements about attacker identity, successful compromise, credential 
theft, attack campaign scale or business impact. A recommendation such as reviewing 
an associated service log is distinguishable from an assertion that the service was 
compromised.
3.16.3 Privacy, uncertainty and reliability
The proposed privacy boundary excludes raw payloads, credentials and unnecessary 
host identifiers. Where endpoint continuity is useful, pseudonymous identifiers can 
preserve within-session relationships without disclosing actual addresses. Retention, 
provider data-handling terms and authorization for cloud processing must be selected 
for the deployment environment. These are proposed controls, not verified properties 
of an existing Gemini integration.
Reliability  requires  timeout  limits,  bounded  retries,  an  input-size  limit  and  an 
idempotent evidence identifier. A cache key includes model, schema and prompt 
versions to prevent reuse of an explanation for different evidence. Invalid JSON, 


--- PDF PAGE 45 ---
33
unknown evidence references, altered probabilities or ungrounded factual claims cause 
the response to be rejected. The fallback is a deterministic template showing the 
verified class, scores and limitations. The design does not allow the language model to 
issue firewall changes or launch diagnostic traffic autonomously.
3.16.4 Explanation acceptance criteria
A  proposed  evaluation  set  should  include  correct  and  incorrect  detections,  low-
confidence cases, missing features, corrupted records, synthetic fallback records and 
prompt-like text embedded in untrusted fields. Acceptance measures include factual 
consistency  with  the  envelope,  evidence-reference  coverage,  numerical  fidelity, 
privacy leakage, refusal on insufficient evidence, and analyst usefulness. Latency and 
API cost are measured separately from capture-to-classification latency. No accuracy, 
usefulness score or runtime estimate is assigned before those experiments exist.

4.8 Training provenance and notebook consistency
The raw local CSV row counts match the eight-file count table recorded early in the 
notebook. The final split and balancing outputs are consistent with the profile artifact’s 
selected population and saved test supports. However, earlier cleaning and selection 
cells retain contradictory outputs. One removal output starts again from 2,830,743 
rows and reports remaining missing/infinite values; a later selection output contains 
only BENIGN and DDoS and gives 2,401,124 rows. Those states cannot be the 
immediate clean five-class input to the recorded final split.
This inconsistency is evidence of non-linear or partially stale notebook execution. It 
does not invalidate the independently checked saved test predictions, but it prevents 
certification of the notebook as a clean top-to-bottom reproduction of the original 
training run. The report accordingly describes training hyperparameters and recorded 
split counts as notebook evidence, while describing metric replay as independently 
executed evidence. No new model training is performed during the reporting task.
Preprocessing is written before the split, including median filling of invalid rate 
values.  That  design  can  expose  information  from  future  evaluation  rows  to  a 
transformation estimated over the complete population. The potential effect is not 
measured here. The row-wise stratified split also does not enforce separation by source 
day, host or session. A stronger protocol would persist split membership and fit every 
learned preprocessing operation only on training data.
4.9 Resolution of the historical feature mismatch
The current feature engine computes timing in microseconds and rates per second. 
Contract tests check duration and inter-arrival units, payload accounting and schema 
order.  The  older  guide’s  warning  that  live  seconds  are  sent  directly  into  a 
microsecond-trained model is therefore not accurate for the audited code. This is a 
supported correction to the implementation account, not a claim that every source of 
live-to-training distribution shift has disappeared.

44
Remaining risks include the inferred historical flag semantics, first-packet duplication 
in length statistics, padding behavior, first-observed direction, FIN segmentation and 
differences among capture platforms. The pipeline applies a 120-second maximum age 
but retains a configurable inactivity rule. Retransmissions and partial captures can 
change packet counts and lengths even if units are correct. The packet simulations 
include a port-scan retransmission sensitivity test, reinforcing that small traffic-shape 
changes can affect predicted labels.

4.12 Runtime observations and implementation costs
A single audit batch prediction for 251,812 rows takes 3.1602 seconds with the 
booster configured for four threads. Model loading and DMatrix construction occur 
before the timed interval. This is an offline inference observation on one host and one 
run. It is not a packet throughput benchmark, a confidence interval, or an estimate of 
the latency experienced by an individual live flow.
Live  latency  includes  flow  completion,  feature  computation,  single-row  DMatrix 
creation, prediction, callback processing and display refresh. Idle flows may wait for 
another packet or a flush before expiration is acted upon. The builder scans active 
flows  during  expiration,  and  completed  results  retain  packet  metadata.  These 
implementation  costs  motivate  future  throughput,  memory  and  packet-loss 


--- PDF PAGE 59 ---

measurements. No unsupported packets-per-second or production-capacity claim is 
derived from the batch timing.
4.13 Threats to validity and supported interpretation
Internal validity is limited by stale notebook outputs, preprocessing before splitting, 
inferred compatibility semantics and absent original live packet captures. External 
validity is limited by the selected five classes, a historical dataset, controlled loopback 
traffic and no independently labelled deployment population. Construct validity is 
limited when a selected profile is used as the expected class: matching that label 
measures conformity to a laboratory stimulus, not necessarily detection of malicious 
intent.
The supported interpretation is that the repository implements a connected packet-to-
flow classifier, reproduces the saved offline labels, and contains recorded laboratory 
evidence of several profile matches. It also retains substantial Brute Force precision 
limitations and presentation-source defects. Those qualifications are integral to the 
result. High aggregate offline metrics support continued engineering investigation; 
they do not establish a production-ready autonomous security system.

5.1 Summary of the investigation
The  investigation  traces  the  MLCN  implementation  from  capture  through 
classification and assesses its evidence at each boundary. The current source contains 
five integrated processing modules, a canonical 24-feature contract, a saved XGBoost 
multiclass model, local CIC flow data, a training notebook, laboratory generators, 
receiver services, launcher utilities and a receiver-aware Streamlit console. The report 
also documents the optional display fallback that can substitute synthetic values for

confusion matrix. Original diagrams document the architecture, while charts report 
verified  class  counts,  scores  and  regenerated  probability  rankings.  Existing  live-
validation  records  are  reconciled  with  their  summary  using  an  explicitly  stated 
method. The institutional document structure is preserved, with unknown student, 
guide and outcome-mapping details left for authorized completion.

5.3 Conclusions derived from the results
First,  a  usable  classifier  integration  depends  on  an  exact  measurement  contract. 
Current MLCN timing features use microseconds, rates use seconds, and payload and 
flag rules are explicitly defined. This repairs the historical timing mismatch described 
in  the  supplied  guide.  The  unusual  compatibility  semantics  remain  important 
limitations when transferring to another extractor or retraining on corrected data.
Second, the saved offline model exhibits strong overall classification performance on 
its recorded test population: 99.4238% accuracy and 99.5568% balanced accuracy. 
These findings are independently reproduced from saved labels and verified by model 
replay. The aggregate result must be read alongside macro F1 of 0.93358 and Brute 
Force precision of 0.53138. The latter corresponds to 799 false positives among 1,705 
Brute Force predictions.
Third, the available laboratory evidence supports selected profile recognition but has a 
narrower interpretation than general intrusion-detection accuracy. Brute Force matches 
only four of five opening flows in the saved validation run. Synthetic final verdicts 
and transformed display probabilities provide no evidence of improved detection. The 
test failures around their labelling show why provenance must be a visible, machine-
checkable property of every reported result.
Fourth, the notebook is informative but not a fully certified reproducibility pipeline. It 
records splits, balancing, hyperparameters and training output, yet its earlier saved 
states are inconsistent. A repeatable training package must preserve preprocessing 


--- PDF PAGE 62 ---
50
decisions, dataset identities, split membership and environment versions. The report’s 
successful inference replay addresses consistency of saved artifacts, not complete 
recreation of training history.
5.4 Contributions and limitations
The principal project contribution is a modular laboratory platform linking captured 
traffic to schema-validated multiclass inference. Its supporting tools allow bounded 
traffic generation, receiver observation and investigation of how flow shape affects 
classification.  The  present  report  adds  a  verified  account  of  those  mechanisms, 
corrected  metric  interpretation,  reproducible  result  extraction  and  an  explanation 
design that keeps factual evidence separate from generated language.
The main limitations are restricted class coverage, incomplete live provenance, weak 
rare-class precision, unresolved test failures in presentation behavior, possible flow-
state  concurrency  and  shutdown  issues,  and  missing  long-duration  performance 
measurements. There is no implemented attribution engine, Gemini reporting service 
or incident database. There is also no controlled comparative benchmark establishing 
that XGBoost outperforms alternative models under an identical protocol.
5.5 Specific future scope
The first priority is trustworthy evidence handling. Demonstration fallback should be 
disabled in evaluation, its source should be unambiguous in every record type, and the 
six failing tests should be resolved through an explicit product decision. A new 
evidence sink should store feature values, schema/model hashes, capture context and 
completion reason alongside genuine predictions. These changes would make later 
error analysis and explanation grounding auditable.
The second priority is repeatable data preparation and evaluation. A clean training 
script should replace state-dependent notebook execution, fit imputation on training 
data, preserve source/session identifiers and create group-aware held-out sets. Raw-
data hashes and extractor versions should be stored with every model. The Brute Force 
decision boundary should then be studied through additional representative benign and 


--- PDF PAGE 63 ---
51
attack flows, validation-only threshold selection, calibration and comparisons with 
matched baselines.
The  third  priority  is  live-system  measurement.  Repeated  authorized  laboratory 
captures  should  vary  operating  system,  interface,  segmentation,  retransmissions, 
background traffic and flow termination. Measurements should include packet loss, 
eligible-flow coverage, failure counts, memory growth and completion-to-prediction 
latency. An explicit stop channel, synchronized shared state and a timed expiration 
mechanism  should  be  evaluated  before  extending  the  system  to  longer-running 
monitoring.
The final priority is the proposed explanation layer. A validated evidence adapter 
should precede any Gemini integration, with privacy minimization, versioned prompts 
and deterministic fallback behavior. SHAP may be evaluated as a separate feature-
attribution component. Human assessment should compare factual correctness and 
usefulness against a simple template before claiming that generated narrative improves 
incident triage.
